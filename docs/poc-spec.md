# ソクトウAI — PoC仕様書

状態：ローカルWhisperの採用を反映した v0.4／2026-09-29

この文書はPoCの実装・評価に用いる仕様書。確定した要件と、未回答のため仮置きしている設計を区別する。未確定事項は末尾にまとめ、実装したことと検証が完了したことを区別する。

## 1. 解決したい課題

営業担当者が商談中に、お客様からの商品・サービスに関する質問に答えられず、「社内で確認して後ほど回答します」と持ち帰ってしまう。

ソクトウAIは、会話の中の質問を検知し、社内資料を検索して、回答候補とその根拠を担当者に提示する。担当者がその場で根拠を確認し、自分の言葉で回答できる状態を目指す。

**提供価値：普段の資料検索と比べ、正しい回答を口頭で伝えるまでの時間を短くし、質問の持ち帰りを減らす。**

AIの回答表示までの時間に加え、担当者が回答と根拠を読み、実際に答えるまでを評価する。

値引き承認や未確定の開発予定など、資料だけでは判断できない質問まで回答することは目指さない。

## 2. 確認済みの要望と仮案

### 確定した要件

| 項目 | 方針 |
| --- | --- |
| プロダクト | ソクトウAI。SaaSとして提供するミニアプリのPoC |
| 利用者 | 顧客の要望をヒアリングし、商材を提案する法人営業 |
| 検証先・利用範囲 | 自分・自社の営業担当者。部署・チーム全体で利用する |
| 商談シーン | オンラインと対面の両方 |
| オンライン会議 | Google Meet・Zoom・Microsoft Teamsのすべて。Zoom・Teamsはデスクトップアプリ版も必須 |
| 端末 | WindowsとMacの両方 |
| 中心機能 | 質問検知 → 社内資料の検索（RAG）→ 回答候補と根拠の表示 |
| 動作 | 検知した質問ごとに自動で検索・表示する。毎回の検索ボタン操作を前提にしない |
| 回答内容 | 商品仕様・料金・導入条件 |
| 参照情報 | 顧客への説明に使える資料・社内FAQに限定する |
| 読む時間 | 商談中に数秒の確認時間を取れる |
| 開発時のデータ | 架空の商材資料・FAQ・模擬商談音声で始める |
| 最終的な検証 | 社内ルールの確認後、実資料・実際の顧客との商談で効果を評価する |
| 開発の優先度 | できるだけ早く。具体的な納期・予算・開発人数は未設定 |
| 実装技術 | フロントエンドはReact、バックエンドはDjango。ユーザーの実装指示に基づく |
| 初期の音声認識 | 公式のOpenAI WhisperをこのPC内で実行する。音声の外部送信なし。ユーザーの指定・選択に基づく |

以下は、提示した推奨案への「はい」を了承として整理した方針。

- 初期は質問への回答候補と根拠の表示に絞る。商材の推薦・次に聞く質問の提案は含めない。
- 会議アプリの横に、小さな別ウィンドウで回答画面を表示する。
- 事前検証で料金・対応可否などの誤断定があれば、修正・再評価してから実商談に進む。

**クラウドAIの社内利用ルールは未確認。架空データでの開発方針への了承を、実商談音声や実資料の外部送信の了承とは扱わない。**

### この仕様書での仮案

| 項目 | 仮案 | 選んだ理由 |
| --- | --- | --- |
| 対応する言語 | 日本語 | 最初の検証範囲を限定する |
| 配布・実装方式 | 小型のWeb画面を第一候補とし、音声取得の実証で確定する | 会議アプリと併用できる構成を先に確認する |
| 検証用商材 | まず架空の1商材 | 正解となる仕様・価格・条件を用意しやすい |
| 参照する情報量 | 5〜20件程度の資料 | 資料の品質と回答精度を分けて検証できる |
| 料金表の取り込み | 初期の架空データは料金と条件を文章のFAQにも整理する | 複雑な表の解析と回答生成の評価を分ける。元のPDF・Excelをそのまま扱う要否は未確定 |
| チームの範囲 | 自社の1部署・1チーム | 部署全体での利用を検証する。具体的な人数・同時商談数は未確定 |
| 共有・権限 | 商品資料・FAQはチーム共有、商談履歴は本人のみ閲覧。資料管理は管理担当者 | 共有範囲の質問は未回答。この方針は提案であり、実データ利用前に確定する |
| 記録の保存 | 実商談の生音声は保存しない。履歴の保持期間は社内基準に合わせて決める | 評価に必要な記録と保存条件を整理する |

仮案は決定事項ではない。具体的な実商材、対応バージョン、音声の取得方法、回答生成のAIサービス、共有範囲・保存期間は未確定として残す。初期の音声認識はローカルWhisperに確定したが、モデルサイズ・処理能力・配布形態は実証で調整する。

## 3. 利用の流れ

### 商談前

1. 利用者が個人のアカウントでログインする。資料管理担当者が、顧客への説明に使える商品資料・FAQを登録する（役割分担は仮案）。
2. アプリが文章を取り出し、検索可能な状態にする。
3. 担当者が登録状況を確認し、「オンライン商談」または「対面商談」を選んで、商談用のセッションを開始する。

### 商談中

1. 担当者が選んだ商談モードに応じて、会議音声またはマイクからの取り込みを開始する。
2. アプリが音声を順次文字起こしする。
3. 質問を検知したら、質問文を画面に表示し、自動で回答処理を始める。
4. アプリが質問と直前の会話をもとに、関連する資料の箇所を検索する。
5. 見つかった箇所に基づく短い回答候補と、根拠の抜粋・資料名・位置を表示する。
6. 担当者が根拠を確認し、お客様に回答する。
7. 担当者が「回答できた」または「要確認」を記録する。商談中に余裕がない場合は終了後に付けられる。

自動検知で拾えなかった質問は、担当者が手入力して検索できる。誤って検知した質問は取り消せる。

### 商談後

検知した質問、回答候補、根拠、担当者が付けた対応結果を一覧で確認する。PoCではこの記録を使って、持ち帰り削減につながったかを評価する。

## 4. PoCに含める機能

| ID | 機能 | 必要な動作 |
| --- | --- | --- |
| F01 | 資料登録 | 資料を追加し、準備中・利用可能・読み取り失敗を確認できる |
| F02 | 資料管理 | 登録資料を確認・削除でき、削除した資料は以後の検索対象から外れる |
| F03 | 音声取り込み | オンライン・対面のモードを選び、開始・停止でき、入力元と取り込み状態がわかる |
| F04 | 文字起こし | 認識途中と確定した発言を区別して表示する |
| F05 | 質問検知 | 確定した発言から質問を抽出し、必要に応じて直前の文脈を補う |
| F06 | 手動質問 | 質問を入力・修正して検索できる |
| F07 | 資料検索 | 質問に関連する箇所を、資料名・位置と一緒に取得する |
| F08 | 回答候補 | 取得した根拠に基づく短い回答と、必要な条件・留意点を表示する |
| F09 | 根拠確認 | 回答から根拠の抜粋と前後の文章を開ける |
| F10 | 回答不能の表示 | 情報不足・根拠の矛盾・検索失敗を区別して伝える |
| F11 | 対応結果・履歴 | 質問ごとに「回答できた」「要確認」を記録し、商談内で振り返れる |
| F12 | チーム利用・ログイン | 利用者を個別に識別し、チームへの参加・利用停止を管理できる |
| F13 | 閲覧・管理権限 | 資料・履歴を許可された利用者だけに提供する。具体的な共有範囲は仮案をもとに確定する |
| F14 | 複数商談の分離 | 複数人の同時利用で、音声・質問・回答・履歴が別の商談に混ざらない |

### 4.1 資料登録

- 初期対応の仮案は、TXT、Markdown、文字を選択できるPDF。
- PDFはページ番号、TXT／Markdownは見出しまたは段落の位置で根拠を示す。
- スキャンPDF、画像、表の複雑な読み取り、外部サービスとの自動同期は初期対象外の仮案。
- 料金表では、金額だけでなくプラン・人数・契約期間・税区分・適用条件を一緒に扱う。架空データでは文章のFAQにも整理する。実資料が表を中心とする場合は、そのまま正確に読めるか確認し、整形する運用か対応形式の拡張を決める。
- 文章を取り出せない資料を、利用可能として扱わない。一部のページを読めない場合もその範囲を表示する。
- サンプル資料を使う場合は、実際の商品情報と区別できる表示にする。
- 更新時は新しい版として登録し、旧版を以後の検索対象から外す。版の自動判定は行わない。
- 以下は削除と履歴の整合性を保つための仮案：検索対象から外した旧版でも、過去の回答に使った抜粋・版・位置は保持期間内で参照できる。画面に「回答時点の資料」と表示し、現行資料と区別する。
- 完全削除を行う場合は、原文・検索用データ・抜粋・その資料を含む回答履歴も削除対象とする。対象を操作前に表示する。実データの削除方針は保存期間・閲覧権限と合わせて確定する。

### 4.2 音声入力

**オンライン商談では、担当者のマイクだけでは相手の音声を取得できない場合がある。相手の発言を確実に取り込める方法の確認が必要。**

| 利用場面 | 必要な入力 | 実装前の確認 |
| --- | --- | --- |
| オンライン商談 | 会議相手の音声。文脈補足のため担当者の音声も利用できるとよい | 対象の会議ツール・OS・ブラウザで音声を取得できるか |
| 対面商談 | 同席者の声を拾えるマイク | 距離・周囲の雑音による文字起こし精度 |
| テキストによる事前検証 | 発言テキスト、または直接入力した質問 | 質問検知・検索・回答の精度を音声と切り分けて評価する |

対応確認の対象は次のとおり。実機確認前の対応保証ではなく、PoCで満たすべき範囲を示す。

| 利用場面 | Windows | Mac |
| --- | --- | --- |
| Google Meet | 相手音声の取得を検証 | 相手音声の取得を検証 |
| Zoomデスクトップアプリ | 相手音声の取得を検証 | 相手音声の取得を検証 |
| Microsoft Teamsデスクトップアプリ | 相手音声の取得を検証 | 相手音声の取得を検証 |
| 対面商談 | マイク入力を検証 | マイク入力を検証 |

Google Meetはブラウザでの利用を初期案とする。Zoom・Teamsについては、利用者をブラウザ版へ切り替えることを対応条件にしない。

- OS・ブラウザ・会議アプリの対応バージョンは音声取得の実証で確定する。古いバージョンや全ブラウザへの対応は未確約。
- スピーカーとヘッドセットの利用、入力・出力機器の変更、権限拒否、会議終了による切断を確認する。
- 開始時に音声が届いていることを確認できるようにする。無音や切断中に「取り込み中」と見せ続けない。
- ブラウザから画面・音声取得APIを使う案では、開始時の取得元選択が必要で、音声を要求しても音声トラックが返らない場合がある。入力の確認を必須にし、ブラウザだけで全対象環境を満たすかは実証する。[W3C Screen Capture仕様草案](https://www.w3.org/TR/screen-capture/#dom-mediadevices-getdisplaymedia)
- 画面取得APIを使う場合も、画面映像は回答生成に送信・保存しない設計とする。会議以外の音が混入する取得方式では、その制約を表示し、必要な入力範囲を検証する。
- 音声取得に補助アプリが必要かは技術検証で判断する。会議ツール内への機能組み込みとは区別する。

オンラインでは相手音声、対面では同席者の発言を取り込めることを、それぞれ必須の検証項目にする。片方だけ動く状態は、今回のPoCの完了とはしない。

### 4.3 質問検知

- 「料金はいくらですか」「既存システムと連携できますか」などの直接的な質問を対象とする。
- 「導入までの期間を知りたいです」など、疑問符がない問い合わせも対象とする。
- 「それは何人までですか」のような発言は、直前の会話から対象を補う。対象が決まらない場合は、担当者が質問を修正できるようにする。
- 挨拶や相づち、単なる説明を繰り返し質問として扱わない。
- 文字起こし途中の同じ発言から、重複した質問を作らない。
- 担当者の質問か顧客の質問かを確実に識別できない入力では、「顧客の発言」と断定しない。発言者の自動識別は必須にしない。
- 複数の質問が続いても、質問と回答の対応を保つ。遅れて返ってきた古い回答で、選択中の別の質問を上書きしない。
- 検知した各質問に対して自動で処理する。新着質問と回答の到着を表示し、過去の回答を読んでいるときに別の質問の回答へ無断で切り替えない。

### 4.4 回答候補と根拠

1件の質問に対して、まず短い回答候補を1つ表示する。複数の言い回しを並べる機能は初期対象外。

表示する内容：

- 検知した質問。
- そのまま口頭回答の参考にできる、原則1〜3文の回答候補。
- 最初に結論を短く示し、その近くに必須条件と短い根拠を置く。詳細な原文は開いて確認できる。数秒で必要な情報を拾えるかを利用者で評価する。
- 回答の成立条件や、担当者が確認すべき点。
- 根拠となる原文の抜粋、資料名、ページ／見出し／段落。
- 根拠の充足状態：「根拠あり」「一部のみ確認」「根拠が見つからない」「資料間で相違あり」。

回答のルール：

- 商品固有の事実は、検索した資料で裏付けられる範囲だけを回答する。
- 価格・対応可否・契約条件などを、一般知識や推測で補完しない。
- 複数の事実を回答するときは、それぞれの根拠を確認できるようにする。
- 根拠がない場合は回答を作らず、「登録資料では確認できません」と表示する。
- 一部だけ答えられる場合は、確認できた部分と未確認の部分を分ける。
- 資料間で内容が異なる場合は、都合のよい一方を採用せず、相違を表示する。
- 根拠の充足状態は正しさの保証として扱わない。裏付けのない「信頼度98%」などの数値は表示しない。
- 資料に書かれた命令文は参照情報として扱い、アプリの動作指示として実行しない。
- お客様への自動返信は行わず、担当者が内容を確認して回答する。

## 5. 画面構成

### A. 商談アシスト画面 — 主画面

オンラインでは会議アプリの横に置く小さな別ウィンドウ、対面では手元のPCで使う。数秒の確認で、回答・必要条件・根拠の要点を読めることを優先する。

| 領域 | 表示・操作 |
| --- | --- |
| 上部 | セッション名、オンライン／対面モード、音声の入力元と取り込み状態、開始・停止 |
| 会話・質問 | 直近の文字起こし、検知した質問、質問の選択・修正・取り消し |
| 回答 | 選択した質問に対する短い回答候補、条件、検索・生成の状態 |
| 根拠 | 引用箇所、資料名、位置、原文を開く操作 |
| 入力・結果 | 質問の手入力、「回答できた」「要確認」 |

狭い表示幅では、選択中の質問・回答・根拠を優先し、全文の文字起こしは開閉できるようにする。

### B. 資料管理画面

登録資料の一覧、追加・削除、登録状況、読み取りエラーを確認する。

### C. 商談内の履歴

質問ごとに回答と対応結果を見返せる。独立した分析ダッシュボードやCRM連携は作らない。

### D. チーム利用の管理

利用者の参加・利用停止と資料管理に必要な最小限の操作を用意する。全社的な組織階層や詳細な営業分析は初期対象外。履歴を管理者や他のメンバーが閲覧できるかは未確定。

## 6. 表示例

以下は表示形式を説明する架空の例。実際の商材の仕様ではない。

> **検知した質問**
>
> 導入するまで、どのくらいの期間がかかりますか？
>
> **回答候補**
>
> 標準構成の場合、お申し込みから利用開始までの目安は2〜4週間です。個別連携が必要な場合は、別途スケジュールを確認します。
>
> **根拠あり**
>
> 「標準構成の導入期間は申込後2〜4週間を目安とする。個別連携の開発期間は含まない。」
>
> 架空の商品導入ガイド／p. 4「導入スケジュール」
>
> ［原文を見る］［回答できた］［要確認］

資料に記載がない質問の場合：

> **検知した質問**
>
> 来月リリース予定の新機能も使えますか？
>
> **根拠が見つからない**
>
> 登録資料では、新機能の提供時期と利用条件を確認できません。担当部署への確認が必要です。

## 7. 処理の構成

フロントエンドはReact、バックエンドはDjangoで実装する。Reactは商談画面・資料登録・履歴・音声入力の操作、Djangoは認証・権限・資料検索・回答処理・保存を担当する。画面とAPIの契約は[api-contract.md](api-contract.md)に整理する。

初期実装ではReact＋TypeScript＋Vite、Django 5.2系＋SQLiteを使う。SQLiteはローカル検証用の選択であり、部署全体の同時利用数を満たすことは別途検証する。APIキーがない標準モードでは登録資料からの抽出検索を行い、生成AI接続済みとは扱わない。外部AI接続用のアダプターを用意し、利用サービスの正式採用・実データ送信条件は未確定のまま維持する。

音声認識は[公式Whisper](https://github.com/openai/whisper)を利用PCのローカルDjangoから実行する。音声を外部AIへ送信せず、認識にAPIキーは使わない。初期実装は日本語の`small`モデル・CPU実行とし、架空のWAVをメモリ上で認識する。モデルサイズは実装上の初期選択であり性能保証ではない。発言を短く区切る方式で、認識途中の文字列を逐次表示する方式とは異なる。全OS・会議アプリの音声取得と認識精度・待ち時間・同時利用数は別途実証する。実商談への利用条件はローカル実行でも確認を継続する。

```text
音声入力 → 文字起こし → 質問の検知・文脈補足 ┐
                                             ├→ 資料検索 → 回答候補・根拠を表示
手入力した質問 ──────────────────────────────┘

資料登録 → 文章抽出 → 箇所ごとに分割 → 検索用データの作成
```

- 検索用データには、元の資料・ページ等の位置を保持する。
- 回答生成に渡すのは質問、必要な会話文脈、検索した根拠。
- 質問ごとに識別子を付け、検索結果・回答・対応結果をひも付ける。
- チーム・利用者・商談にも識別子を付ける。取得・検索・保存の各処理で権限を確認し、画面上の非表示だけに頼らない。
- 検索方式、回答生成モデル、運用時のデータベースは正式選定前。音声認識の初期方式はローカルWhisperとし、実データへの適用は社内利用条件の確認後に決める。
- APIキーなどの認証情報は画面に配信せず、サーバー側で扱う。

## 8. 待ち時間とエラー時の動作

### 応答時間の仮目標

「リアルタイム」の評価基準を、商談で待てる時間として定義する。以下は性能保証ではなく、PoCで測定する仮目標。

| 指標 | 仮目標 | 測定の起点と終点 |
| --- | --- | --- |
| 質問の表示 | 95パーセンタイル2秒以内 | 質問発話の終了 → 検知した質問の表示 |
| 回答候補の表示 | 中央値5秒以内、95パーセンタイル8秒以内 | 質問発話の終了 → 根拠付き回答の表示完了 |
| 正しい口頭回答まで | 普段の資料検索より短縮する | 質問発話の終了 → 担当者が正しい回答を伝えるまで。読む・確認する時間を含む |

文字起こしにかかった時間も含める。オンライン6組み合わせと対面の両OSで結果を分けて記録する。手入力での計測も別に記録する。

未検知・処理失敗・時間切れを記録から除外しない。30秒で完了しないものは「30秒超・未完了」と記録し、成功した試行だけの応答時間で合格としない。回答不能は状態表示までの時間を記録するが、正しい回答に成功した件数には含めない。

同時利用数も併記する。部署全体の利用人数・同時商談数が未確定のため、単独利用の結果を部署全体の性能保証にしない。

### 状態の扱い

- 処理中は「質問を検知」「資料を検索中」「回答を作成中」を表示する。
- 10秒を超えても終わらない場合は遅延を表示する。30秒で打ち切り、再試行できるようにする。時間は検証後に調整する。
- 検索に成功して該当箇所がなかった場合と、通信障害で検索できなかった場合を区別する。
- 音声取得の拒否・非対応・切断は画面に表示し、手入力を使える状態を保つ。
- 中断・再試行でも、別の質問に回答がひも付いたり、同じ質問の履歴が無制限に増えたりしない。

## 9. PoCのデータの扱い

- 開発・初期評価では、架空の商品仕様書・料金表・FAQと模擬商談音声を使う。画面でも架空データとわかる表示をする。
- 実資料は、検証への利用と顧客への説明が認められたものに限定する。クラウドAIへ送信できるかは別の確認事項。
- クラウドAIの社内ルールは未確認。実データへ切り替える前に、利用可能なサービス、送信する音声・テキスト・資料の範囲、保存・保持条件、商談での音声利用の運用を確認する。
- 実商談の生音声はアプリに保存しない方針を仮案とする。架空の音声素材は検証用に保持できる。
- 質問・回答・根拠・対応結果・応答時間は評価用に記録する。実商談の履歴の保存先・保持期間・削除方法は、実データを使う前に確定する。
- 利用者は個別に識別し、ログインした所属チームのデータだけを扱う。複数人の商談でデータを混在させない。
- 未回答の共有方針は、仮に「商品資料・FAQはチーム共有、商談履歴は本人のみ閲覧」とする。管理者による他者履歴の閲覧や、履歴のチーム全体公開は決定していない。
- 仮の役割分担は、管理担当者が利用者と参照資料を管理し、営業担当者は資料を検索して自分の商談を操作する形。権限・共有・保持方針を確定し、確認するまでは実商談データでのチーム運用を始めない。
- 初期の提供先は自社の部署・チーム。複数企業への一般提供と課金はPoCの範囲に含めない。

## 10. 初期PoCの対象外

- Zoom／Teams／Google Meetそれぞれへのネイティブ組み込み。
- CRM、Slack、社内ドライブなどとの自動同期。
- 複数企業・複数部署の複雑な権限管理、課金。自社チームのログインと最低限の管理・権限確認はPoCに含める。
- 顧客への自動送信、値引き・契約条件の自動判断。
- 議事録の自動要約、営業評価、次の提案の自動生成。
- 画像・スキャン資料のOCR、高度な表・図の解釈（取り込み形式は仮案。実料金表をそのまま扱う必要があれば見直す）。
- 多言語対応、完全な話者識別。

## 11. 検証方法と成功条件

### 検証セット

最初は架空の商材の商品仕様・料金・導入条件から、少なくとも次を準備する。社内確認後の評価では、実資料に基づく別の検証セットを用意する。音声経路はオンライン6組み合わせと対面の両OSで実施し、結果を分けて記録する。

- 資料に答えがある質問：30件。
- 資料に答えがない質問：10件。
- 質問ではない発言：20件。
- 境界例：曖昧な指示語、資料間の矛盾、連続する質問、文字起こしの誤り、通信失敗。
- 料金の条件違い、旧版と現行版、複数人の同時商談、閲覧権限のない履歴へのアクセス、資料削除後の引用表示。

答えがある質問には、正解となる資料箇所と、回答に必要な条件を人が付ける。調整に使った質問と、最終評価の質問は分ける。

### 仮の合格基準

| 観点 | 判定方法・仮目標 |
| --- | --- |
| 質問を拾えるか | 対象質問の90%以上を検知する。質問ではない20発言に対する誤検知は2件以下 |
| 正しく答えられるか | 答えがある30問のうち27問以上で、必要条件を含む正しい回答と対応する根拠が得られる。残りは回答不能・要確認として扱い、誤答の許容枠にしない |
| 根拠を確認できるか | 回答に示した引用が元資料の該当箇所へたどれる。存在しない資料・箇所の引用は0件 |
| 不明なことを断定しないか | 答えがない10問すべてで、不明と表示する。価格や可否などの根拠のない断定は0件 |
| 誤断定が起きた場合 | 料金・対応可否・契約条件などの誤断定は修正・再評価の対象。引用が存在しても条件の読み違いは誤答とする。未修正のまま実商談へ進まない |
| 商談の速さに合うか | 各対象環境で前節の応答時間を測定し、原文確認を含む口頭回答までの時間を普段の検索と比較する |
| 持ち帰り削減につながるか | 資料に答えがある質問の持ち帰りを、普段の検索と比べて半減させることを仮目標とする。全質問の持ち帰り率も別に記録する |
| チームで使えるか | 定めた同時商談数で、応答時間と商談・権限の分離を満たす。具体的な人数・同時商談数は未確定 |

回答の正誤と根拠の妥当性は、商材を理解する人が確認する。「回答できた」ボタンの記録だけで正解と判定しない。

口頭回答時間と持ち帰りの比較では、質問数・商談数・担当者の経験・評価期間を事前に記録する。同程度の難しさの質問を使い、同じ質問を繰り返したことによる暗記の影響を避ける。正しく回答できなかった試行は、速く終わっていても短縮成功としない。

架空データでの合格は仕組みの動作確認。実際の持ち帰り削減効果は、社内確認後の実資料・実商談で評価する。数値の閾値は仮案であり、ユーザーが指定した確定値ではない。

これらは小規模なPoCの判定基準であり、実商談全体での精度や効果の保証には使わない。

### 機能の受け入れ条件

- 登録・削除した資料が、検索対象に正しく反映される。
- オンラインでは会議相手の質問音声、対面では同席者の質問音声を取り込み、どちらも回答候補と根拠まで表示できる。
- 手入力・質問修正からも同じ検索と回答の流れを使える。
- 根拠不足や通信失敗で、以前の回答を今回の回答のように表示しない。
- 連続する質問で回答の順番が入れ替わっても、対応関係が壊れない。
- 音声取り込みを停止した後は、新たな音声処理を行わない。
- 別の利用者・商談の音声、質問、回答、閲覧権限のない履歴が混ざらず、取得できない。
- 利用停止・権限変更が有効になり、ログイン画面だけでなくサーバー側でアクセスが制限される。
- 資料を検索対象から外す操作と完全削除の結果が、履歴・引用・検索データに対して定義どおりになる。
- チームでの実商談利用を含めて評価し、架空データだけのデモでPoC完了としない。

## 12. 段階的な検証順序

1. **架空データでの土台作り**：商品仕様書・料金・FAQ・模擬商談と正解データを用意する。
2. **音声取得と回答処理の早期確認**：会議アプリ・OSの各組み合わせで音声取得を確認する。同時に、テキストから検索・回答・根拠表示までの処理を検証する。
3. **模擬商談とチーム利用**：音声からの一連の動作、個人ログイン、権限、同時商談、短時間で読める表示を検証する。
4. **実データへの移行条件を確定**：AI利用の社内ルール、資料・履歴の共有範囲、保存・削除条件、商談での音声利用の運用、実資料と評価担当者を確認する。
5. **実商談での評価**：自社の部署・チームで利用し、普段の検索と比べた口頭回答時間・持ち帰り・誤回答を記録する。

テキストのみの試作や単一環境での動作は中間段階。両OS・全3会議ツール・対面での音声経路と、自社チームでの実商談評価までが今回の対象。できるだけ早く進めるため、架空データによる技術検証と社内条件の確認は並行できる構成にする。

## 13. 未確定事項と扱い

追加ヒアリングはここで区切る。以下は決定済みと扱わず、試作中に確認できる項目と、実データの利用前に確定する項目を分けて管理する。

| 確認する時点 | 未確定事項・扱い |
| --- | --- |
| 試作中 | 対応OS・ブラウザ・会議アプリのバージョンと音声取得方式。実証結果を対応表に記載する |
| 試作中 | 初期資料の形式。料金FAQ化は仮案、実際のPDF・Excel料金表をそのまま扱う要否は未回答 |
| 試作中 | ログイン方式、検索方式、回答生成サービス、保存先、部署の人数と同時商談数。Whisperのモデルサイズ・実行性能・配布方法は実証する |
| 実データ利用前 | クラウドAIの社内利用条件。未確認のまま実商談音声・実資料を外部へ送らない |
| 実データ利用前 | 資料と商談履歴の閲覧・管理権限。チーム共有資料・本人のみの履歴は未回答事項に対する仮案 |
| 実データ利用前 | 記録の保持期間・削除方法・商談での音声利用の運用 |
| 実商談の評価前 | 実商材、使える資料、正誤判定者、質問数・商談数・評価期間、数値目標 |
| 開発着手時 | 開発人数・費用・最初の検証日。「できるだけ早く」を優先するが、現時点で完成日を確約する根拠はない |
